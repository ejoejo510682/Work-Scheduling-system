排班演算法原型 — GitHub issue #4

這個頁面要回答的問題：「每週排班規則」能不能寫成一套可以自動跑的演算法？ 各規則先後順序對不對、規則互相衝突時該讓誰優先、人力真的不夠時要怎麼降級、 而且要能明確告訴 Cynthia「這週哪裡有問題」。

下面所有名字、人數、能力都是假資料，只是用來測試排班邏輯是否合理， 不是公司目前真正的班表。點選下方分頁可以看幾種「刁鑽情境」的示範， 或往下拉到「自由調整」區塊自己試著改資料看看結果會怎麼變。

自由調整（改完按「重新產生班表」）

手動調整（鎖定）＋重排整週

模擬 Cynthia 在草稿上手動改格子：手動指派的格子會被「鎖定」，按「重排整週」時鎖定的格子一律不動， 其他格子全部重新計算。重排後跟上一次結果不一樣的格子會用黃框標出來。
「主要／備援」選備援時：只能設在這個人這個時段已經有主要任務的格子（主要任務會一起鎖定），備援崗位這個時段要有開； 不限預設的「撿貨 → 包裝」。能力不夠、包裝超過 4 人（含備援）只會提醒，不會擋。

目前鎖定的格子：

    這一週的班表

    第一任務 備援（第二任務） 手動鎖定（含有指定人員的本週任務） 任務（固定任務、系統挑人的本週任務） 重排後有變動的格子

    草稿提醒

      印單第三天與任務

      正職印單第三天怎麼選出來的，以及每一筆任務（固定任務、本週任務）的處理結果：排入、代班、跳過（那個時段已經有別的主要工作，例如印單）、留空。

      非出貨時段：週一 vs 週三

      出貨崗位只開在「出訂單後」。其他時段（上午出訂單前、下午出訂單前、出貨完成後）沒排到崗位的 PT， 每天都去處理進貨（只補當天本來就有上班的人）。出貨組正職只自動排出貨工作（出貨崗位、印訂單）， 這三個時段除了印單跟任務（例如處理退貨的固定任務）之外都「不排」，留給 Cynthia 手動安排（第九、十二次補充決議）； 進貨組的正職連陳軒照進貨組規則，照常自動排處理進貨。

      這週六怎麼挑人（週六輪流）

      每個人「上次上週六」的日期讀自過去幾週的班表；離上次最久（或從沒上過）的人優先，同樣久時再用既有挑人順序。 PT 先分成「三級崗位多／少」兩群，各群內輪流，維持 2 位多＋1 位少。

      純邏輯模組在 scheduleLogic.js（跟這個 HTML 放在同一個資料夾）， 純函式、沒有畫面邏輯，日後驗證沒問題可以直接搬進正式專案的 src/lib/。 這個 HTML 頁面本身是原型用的畫面，不會進正式專案。
